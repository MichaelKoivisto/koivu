# Koivu Bootstrapping Architecture: T-Diagrams

**Status:** Architecture Blueprint  

**Component:** Global  

> Capt. Barbossa: So you expect to leave me standing on some beach with nothing but a name and your word it's the one I need and watch you sail away on my ship?<br>
> Capt. Jack Sparrow: No. I expect to leave you standing on some beach with absolutely no name at all, watching me sail away on *my* ship, and then I'll shout the name back to you. Savvy?<br>

This document maps out the bootstrapping pipeline of the **Koivu** compiler infrastructure. It uses classic **T-diagrams** to show how the project transitions from an external host dependency (LLVM) to a fully self-hosting compiler.

### T-Diagram Notation Recap
A compiler T-diagram represents:
* **Left:** The source language being compiled.
* **Right:** The target language produced.
* **Bottom:** The language the compiler itself is written in.

---

## 1. Stage 1 (Seed): The External LLVM Scaffold
In the initial phase, Stage 1 is written directly in **LLVM IR**. Because there is no Koivu executable yet, an external host tool (`llc`) must compile it into target machine code (e.g., `x86_64`).

```text
       +-----------------------+

       |       Stage 1         |
       |       Source          |
       +-------+       +-------+

               |       |
       +-------+-------+-------+

       |   LLVM   -->  x86_64  |
       |   IR                  |
       +-------+       +-------+

               |       |
               |  llc  |  <--- (External LLVM Static Compiler Executable)
               +-------+
```
* **Status:** This is pure **bootstrapping via a host compiler**. 

---

## 2. Stage 2 (Bridge): Building the Macro-Expanding Compiler
Now that we have a working **Stage 1 Executable** (running natively on `x86_64`), we use it to compile the Stage 2 source code. Stage 2 introduces hygienic macros and closures.

```text
       +-----------------------+

       |       Stage 2         |
       |       Source          |
       +-------+       +-------+

               |       |
       +-------+-------+-------+

       | Stage 1  -->   LLVM   |
       |  Lisp          IR     |
       +-------+       +-------+

               |       |
               | x86_64|  <--- (Stage 1 Binary compiled in Step 1)
               +-------+
```
* **Output:** This step outputs **Stage 2 written in LLVM IR**. 
* **Follow-up step:** This output is fed back into LLVM `llc` to generate a **Stage 2 Executable** running natively on `x86_64`.

---

## 3. Stage 3 (Production Core): The Nanopass Scheme Compiler
Using the **Stage 2 Executable**, we compile the initial implementation of Stage 3 (the statically typed Scheme dialect featuring the Nanopass architecture). 

```text
       +-----------------------+

       |       Stage 3         |
       |       Source          |
       +-------+       +-------+

               |       |
       +-------+-------+-------+

       | Stage 2  -->   LLVM   |
       |  Lisp          IR     |
       +-------+       +-------+

               |       |
               | x86_64|  <--- (Stage 2 Binary generated in Step 2)
               +-------+
```
* **Output:** This step outputs the initial **Stage 3 compiler written in LLVM IR**.
* **Follow-up step:** Just like before, LLVM `llc` compiles this IR into the **Stage 3 Executable (Version A)**.

---

## 4. Achieving Meta-Circularity: The Self-Hosting Stage 3
Once the Koivu project implements its [native target backend](backend.md) directly inside the Stage 3 Scheme source code, the project can drop its LLVM dependency entirely. 

To achieve full self-hosting and verify correctness, the compiler goes through a **cycle fixpoint test**:

### Step 4A: Compiling Stage 3 with the LLVM-built Executable
We feed the new Stage 3 Source (which now includes the native backend) into the **Stage 3 Executable (Version A)**.

```text
       +-----------------------+

       |       Stage 3         |
       |       Source          |
       +-------+       +-------+

               |       |
       +-------+-------+-------+

       | Stage 3  -->  x86_64  |
       | Scheme                |
       +-------+       +-------+

               |       |
               | x86_64|  <--- (Stage 3 Version A: Emits x86_64 but contains LLVM artifacts)
               +-------+
```
* **Output:** This outputs **Stage 3 Executable (Version B)**. Version B is compiled entirely natively, but its binary was still generated by a compiler that originally touched LLVM.

### Step 4B: Pure Meta-Circular Self-Hosting (The Ultimate Goal)
To break the final conceptual link to LLVM, **Version B** is used to compile the **Stage 3 Source** one final time.

```text
       +-----------------------+

       |       Stage 3         |
       |       Source          |
       +-------+       +-------+

               |       |
       +-------+-------+-------+

       | Stage 3  -->  x86_64  |
       | Scheme                |
       +-------+       +-------+

               |       |
               | x86_64|  <--- (Stage 3 Version B: Pure native Koivu binary)
               +-------+
```
* **Output:** This outputs **Stage 3 Executable (Version C)**. 
* **The Meta-Circular Loop:** When `Version B` and `Version C` are byte-for-byte identical, the compiler has reached a fixpoint. The language description is now fully maintaining, interpreting, and compiling itself. 

At this point, the external LLVM scaffold is completely discarded, and a true **meta-circular dependency** is achieved.
